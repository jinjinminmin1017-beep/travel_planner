# 测试任务：本地铁路时刻表快照与实时核票

> 对应开发任务：`docs/Dev/task_from_arc_for_dev_20260804_rail_timetable.md`。

## 测试原则

- 默认全部使用脱敏 fixture 和 fake Provider，不在自动化测试中访问 12306 或 FlyAI。
- 真实网络 smoke 必须显式 opt-in、低频、有日期/站点范围和调用上限，且不得绕过验证码或限流。
- 分开验证“时刻表存在”和“实时可购”，任何情况下不得用前者替代后者。

## P0-1：导入解析与过滤

- station 目录能稳定解析 telecode、站名和拼音字段，异常行被报告而非静默吞掉。
- 车次发现响应能提取 `service_date`、`train_no_internal`、车次号、始发站和终到站。
- 完整停站响应按 `stop_sequence` 排序，始发站 arrival 可空、终到站 departure 可空。
- G/D/C 被保留，其他前缀按配置排除；同日同内部车次重复响应只生成一个服务。
- 过期 `train_list.js` fixture 被识别为不可用于当前日期，不进入 active 批次。
- 响应结构缺字段或漂移时批次失败，并输出脱敏、可诊断错误。

## P0-2：checkpoint、幂等与限流行为

- 导入在站点发现中途终止后，`--resume` 从未完成项继续。
- 在车次详情中途终止后，已完成服务不重复请求/重复写入。
- 同一输入完整导入两次，`rail_service` 和 `rail_stop_time` 行数不变。
- 暂时网络错误按上限退避；超过上限后记录失败并结束，不无限重试。
- 验证码、429 或访问限制触发暂停/checkpoint，不尝试自动解决挑战。
- 默认单线程且请求间隔生效；dry-run 不修改 active 快照。
- bootstrap 从近到远补全 D0～D+14；中断恢复后最终 15 个日期均达到 ACTIVE 且没有重复数据。
- refresh 新增 D+14、移出过期日期，并对 D0～D+13 完成差异校正。
- 调度错过一天后，下一次 catch-up 能补齐窗口缺口。

## P0-3：数据库约束与批次激活

- `(batch_id, train_no_internal)` 唯一约束有效，同一车次允许在新 STAGING 批次与上一 ACTIVE 批次中同时存在。
- 同一服务日同时只能有一个 ACTIVE 批次；激活切换必须在事务中完成。
- `(service_id, stop_sequence)` 唯一约束有效，孤立 stop 被外键拒绝或清理策略明确。
- 到达和发车 day offset 可独立保存，跨午夜绝对时间正确。
- staging 批次全部校验成功后才切换 active；失败或中断不覆盖上一批次。
- 新增、取消和摘要变化车次在 refresh 后均正确；发现遍历未完整结束时不得把旧车次判为取消。
- 每个服务日保留上一成功批次可回滚，超过保留期的 RETIRED 批次才允许清理。
- 旧计划与既有票务表在 migration 前后可正常读取。
- 用查询计划验证直达和换乘 SQL 命中目标索引，无全表扫描回退。

## P0-4：直达搜索

- 同一服务中 A 序号小于 B 时可找到 A->B。
- 反向 B->A 不得误用同一车次。
- 车次跨午夜时总耗时正确，不出现负数或 24 小时偏差。
- 始发站 arrival 为空、终到站 departure 为空不影响合法路段。
- 日期无覆盖、快照过期、本地确实无车返回不同诊断状态。
- 候选数上限与排序稳定，输入顺序变化不改变等价结果。

## P0-5：一次换乘搜索

- 第一段到达 + 安全窗口 <= 第二段发车时可换乘。
- 少于安全窗口的方案被剔除；边界等于安全窗口时按产品规则确定性处理。
- 跨日换乘可正确组合，但超过日期/等待/总时长上限会被裁剪。
- 同站换乘与需要跨站换乘不得混淆；第一期不支持的跨站换乘必须显式排除。
- 两段车次方向和上下车序号均正确。
- 禁止产生两次以上换乘，候选组合数保持有界。

## P0-6：站点语义与 hub_rank 回归

- 输入“宜兴”时，宜兴站进入首批候选且不会被无锡站、无锡东站截掉。
- 输入“宜兴站”时，明确站名匹配权重高于城市枢纽和 `hub_rank`。
- 输入“无锡”时，可按既有规则覆盖无锡站、无锡东站等合理候选。
- 强匹配候选先保留，剩余槽位才按相关性、距离、`hub_rank` 分配。
- 同名站点、区县与地级市边界 fixture 结果稳定，候选总数受限。

## P0-7：FlyAI 分组与候选匹配

- 同一 `(service_date, origin, destination)` 的多个候选只触发一次 FlyAI 查询。
- 不同日期或站点对不会错误合并。
- 日期、车次号、起终站和时间均匹配时才关联；歧义结果 fail-closed。
- 完整价格、席别/余票语义和 `jumpUrl` 使状态变为 `AVAILABLE`。
- 明确无票为 `SOLD_OUT`，未开售为 `NOT_ON_SALE`，来源故障为 `PROVIDER_UNAVAILABLE`。
- 缺价格、缺 jumpUrl、结构漂移、非零退出或 stderr 异常均不得发布路线卡。
- 无票会尝试下一候选组；达到调用数/总时长预算后停止。
- 只有超时、限流按策略有限重试；确定性空结果和进程崩溃不循环重试。

## P0-8：Planner 集成与回滚

- 两个功能开关关闭时，铁路规划调用链与基线一致。
- 快照有效且开关开启时，先本地搜索再核票，不再为每个枢纽组合做路线发现。
- 快照过期/缺日期时走旧路径，本地真实无车不会错误触发同一路径的无界扩张。
- 最终 API 只包含已验证方案，schema version 和现有前端类型不变。
- 直达、换乘和混合路线不会重复核验同一站点组。
- 既有 fingerprint、票价、席别、redirect 关联测试继续通过。

## P1：性能与容量

固定数据集至少覆盖：

- 15 个服务日。
- bootstrap、正常每日 refresh、连续漏跑后 catch-up 和单日期刷新失败四种生命周期场景。
- 多个始发终到、跨日、短途密集停站和一次换乘枢纽。
- 足够数据量以暴露全表扫描和 Python 全量建图问题。

验收指标：

- 本地直达搜索 P95 <= 100ms。
- 本地一次换乘搜索 P95 <= 500ms。
- 典型铁路规划外部查询 <= 3 组。
- 导入内存稳定，服务/停站数线性增长时无明显超线性耗时。
- 报告 cold/warm P50/P95/P99，不把 fixture 预热结果当成真实网络端到端指标。

## P1：真实低频 smoke（手工/显式启用）

- 只选择少量日期、站点和车次，记录调用上限、间隔和执行时间。
- 验证当前响应可解析、checkpoint 可恢复、日志不包含 Cookie/凭据。
- 验证 FlyAI 返回的同站点对多车次可与本地候选关联。
- 若出现验证码、429、访问限制或 FlyAI 运行时未认证，停止 smoke 并记录门禁未通过，不改用绕过方案。

## 回归范围

- 后端单元与集成测试。
- API schema 校验与前端类型检查。
- 现有地点解析、多站点查询、铁路直达/换乘、混合规划、缓存、熔断和 redirect 测试。
- 数据库 migration 前向验证及旧计划读取回归。

## 测试交付物

- 脱敏的站点、车次发现、完整停站和 FlyAI 核票 fixtures。
- 单元、集成、migration、查询计划和性能测试报告。
- 一份启用/关闭功能开关的对照结果。
- 真实 smoke 如未执行，必须明确标记“未验证真实网络”，不得以 fixture 通过替代。
