# 开发任务：铁路站点坐标全量补齐与门到门候选排序

> 来源：`docs/ARCHITECTURE.md` 10.6“铁路站点地理目录与候选排序（已批准目标，待实现）”。
> 优先级：P0。当前3397条铁路站点中只有15条内部 seed 带坐标，3382条12306目录站点均无坐标，不能可靠支持附近车站规划。

## 目标

- 为全部12306铁路站点建立可审计的坐标解析状态，并让所有 `planning_enabled` 客运站达到100%可信坐标覆盖。
- 使用 `station_code` 合并12306目录、内部 seed 和坐标来源，消除重复车站实体。
- 普通地址/POI按真实接驳和运行图可达性选择车站，禁止子串伪强匹配和缺坐标 `hub_rank` 兜底。
- 在有界查询预算内比较多个出发站、到达站组合，禁止第一组车次填满展示数量后提前结束。
- 不改变外部 API schema，不把未经实时核票的本地候选发布为可用计划。

## P0-1：冻结数据模型与来源边界

涉及文件：

- `backend/app/data/transport_nodes.json`
- `backend/app/data_sources/transport_catalog_providers.py`
- `scripts/import_transport_nodes.py`

任务：

- 以12306 `station_code` 作为铁路站点稳定实体键；名称和别名不能代替唯一标识。
- 坐标是站点级主数据，唯一键为 `station_code`；禁止把 `service_date`、车次、查询日期或规划请求写入坐标唯一键。
- `rail_service`、`rail_stop_time` 和每日D0～D+14快照只保存/引用 `station_code`，不得为每个服务日期复制 `latitude`、`longitude` 或坐标来源元数据。
- 站点身份来源与坐标来源分离。坐标字段至少记录：
  - `coordinate_source_id`
  - `coordinate_source_version`
  - `coordinate_updated_at`
  - `coordinate_quality`
  - `coordinate_resolution_status`
  - `planning_enabled`
- `coordinate_resolution_status` 至少区分 `VERIFIED`、`AMBIGUOUS`、`NOT_FOUND`、`INVALID`；只有 `VERIFIED` 可进入规划。
- 坐标来源必须满足项目许可证和商业使用门禁；不得抓取未批准页面、绕过访问控制或把推测坐标标为真实数据。
- 记录当前基线统计：铁路站点总数、各来源数量、坐标覆盖率、重复实体数和未解析数。

验收：站名来源不会被展示成坐标来源；所有站点都有明确解析状态。

## P0-2：实现可恢复的坐标补全流水线

建议新增：

- `scripts/enrich_rail_station_coordinates.py`
- 坐标来源 adapter 或导入 fixture
- 脱敏质量报告目录

任务：

- 输入12306目录的 `station_code`、规范站名、城市和别名，向已批准坐标来源解析铁路站点。
- 先按 `station_code` 查询活动坐标目录；已有 `VERIFIED` 坐标且来源版本未变化时直接复用，不发起新的地理编码请求，也不新增坐标记录。
- 支持 `--dry-run`、`--checkpoint`、`--resume`、来源级 QPS、超时、缓存和有限重试。
- 规划请求不得触发全量或批量地理编码；在线只读取已激活目录。
- 对每条结果执行经纬度类型、合法范围、中国边界、城市归属、站点名称/类别和重复距离校验。
- 同名多站、名称变更、迁址和城市不一致进入 `AMBIGUOUS`，不得自动选择第一个搜索结果。
- 先写 staging 目录和报告；校验全部通过后原子替换活动目录，中断或失败不得产生半成品。
- 质量报告至少输出总数、VERIFIED/AMBIGUOUS/NOT_FOUND/INVALID 数量、覆盖率、来源版本和坐标大幅变化清单。
- 只有来源版本更新、站点迁址/更名、原记录非 VERIFIED 或显式 `--force-revalidate` 时允许重新解析；更新同一 station code 的主记录并保留必要审计信息，不按日期追加副本。

验收：任务可中断恢复；重复运行幂等；同一站点覆盖多个服务日期时坐标查询和活动记录均为1；失败不覆盖上一活动目录。

## P0-3：按 station_code 合并重复车站实体

任务：

- 修正现有 merge key，内部 seed 能在获得 station code 后与12306记录合并，而不是形成两个同名规划候选。
- 合并时保留12306电报码和别名，同时保留通过验证的高质量坐标及其独立来源。
- station code 冲突、同名不同 code、同 code 坐标大幅偏移必须 fail-closed 并进入报告。
- 对上海虹桥等现有 seed/12306重复记录执行迁移和回归验证。
- 不允许通过简单名称 contains 合并跨城市或同名站。

验收：每个 station code 最多一个活动铁路节点；活动候选中不存在同一车站重复实体。

## P0-4：修复站点语义匹配

涉及文件：

- `backend/app/services/location_resolver.py`
- 交通节点归一化和候选诊断模块

任务：

- 用户明确输入完整站名时，规范站名或登记别名可形成精确匹配。
- 普通地址、社区、酒店和POI不得因站名是输入前缀/子串而形成强匹配。
- 删除“上海南”命中“上海南翔格林公馆”这一类规则；不得用最短字符串或城市前缀猜站。
- 缺坐标、坐标非 VERIFIED 或 `planning_enabled=false` 的站点不得进入距离候选，并记录稳定排除原因。
- `hub_rank` 仅作为所有主要门到门指标近似相同时的弱 tie-breaker，不能代替坐标或接驳事实。

验收：上海南翔格林公馆不强匹配上海南站；明确输入“上海南站”仍精确命中上海南站。

## P0-5：按真实接驳和运行图生成候选站

涉及文件：

- `backend/app/services/location_resolver.py`
- `backend/app/services/local_transfer_engine.py`
- `backend/app/services/rail_route_search.py`

任务：

- 对出发地和到达地分别地理编码；先按直线距离做有界预筛，再调用地图 Provider 计算道路时间、距离和费用。
- 候选排序先考虑可验证接驳成本和用户约束，再考虑本地运行图可达性；物理最近但目标时间无可达车次的站点不能直接胜出。
- 出发端与到达端使用相同原则；“苏州”不能未经比较就选择造成超长末程接驳的苏州南站。
- 对地图失败、地点歧义和无可用附近站返回明确诊断，不生成估算接驳数字。
- 控制候选数量和地图调用预算，但截断原因必须可观测。

验收：候选日志包含坐标来源、直线距离、地图接驳、运行图可达性、排序因子和排除原因。

## P0-6：修复站点对提前返回并执行全局比较

涉及文件：

- `backend/app/services/planner.py`
- `backend/app/services/rail_inventory_verifier.py`
- `backend/app/services/offer_preselection.py`

任务：

- 不得因为第一个站点对返回的车次已达到 `max_plans` 就跳过其他高优先级站点对。
- 先通过本地运行图和接驳成本形成有界站点对，再按预算进行FlyAI分组核票。
- 对已核验方案统一比较完整门到门总时间、总费用、换乘次数、接驳风险和用户偏好。
- 展示数量 `max_plans` 只用于全局排序后的结果裁剪，不能作为停止站点探索的条件。
- 对核票组数、跳过站点对、预算耗尽和最终淘汰原因增加诊断。

验收：首个站点对返回10条车次时，仍会按预算检查排名更高或相近的其他站点对，再从全局候选中选出结果。

## P0-7：完整性门禁、可观测性与回滚

任务：

- 发布门禁：所有 `planning_enabled` 铁路客运站坐标覆盖率必须为100%。
- 原始目录中的未解析站点允许保留，但必须 `planning_enabled=false`，且不能被描述为已支持附近车站规划。
- 启动或CI检查活动目录的重复 station code、空坐标、非 VERIFIED 坐标、越界坐标和来源元数据缺失。
- 启动或CI检查坐标数据不存在 `service_date` 维度，任意数量的铁路服务日都只能引用同一条 station code 坐标主记录。
- 指标至少包含坐标覆盖率、禁用站点数、候选排除原因、平均候选数、地图调用数和首组提前停止次数；后者目标为0。
- 坐标目录保留上一活动版本；新目录异常时原子回滚。Planner回滚可关闭本地铁路路由开关，不删除历史计划。

验收：任何门禁失败均阻止新目录激活，不影响上一有效版本。

## 开发顺序

1. P0-1先冻结实体键、字段和来源许可。
2. P0-2与P0-3完成后生成可激活的坐标目录。
3. P0-4修复语义误匹配，可与坐标导入并行开发。
4. P0-5依赖已验证坐标；P0-6依赖本地运行图候选和核票器。
5. P0-7门禁、回滚和测试全部通过后才能启用新排序。

## 完成定义

- 全部12306站点都有坐标解析状态；所有 `planning_enabled` 客运站坐标100% VERIFIED。
- 活动目录按 station code 唯一，不存在 seed/12306重复车站。
- 相同站点跨日期规划复用同一坐标，不重复调用坐标来源，也不按日期重复记录经纬度。
- 南翔回归中不再把上海南翔格林公馆匹配为上海南站，南翔北和上海虹桥按真实接驳与可达车次参加比较。
- 苏州到达端也执行真实末程接驳比较，不再未经比较接受约51公里接驳。
- 第一站点对返回足量车次不会触发提前结束；最终结果来自有界全局门到门排序。
- 后端全量测试、数据质量检查和相关低频 smoke 通过；未执行真实来源验证时必须明确标记，不能用 fixture 宣称全量坐标可用。
- 外部 API schema 不变；若实现需要暴露新诊断字段，必须暂停并先更新 `docs/API_CONTRACT.md`。
